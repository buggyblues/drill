# 技术架构

## 一、总览

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Electron   │   │     Web     │   │     iOS     │
│  完整本地库  │   │   无本地库   │   │ 缓存 + 队列  │
│   全功能     │   │  临时查看    │   │ 查看 + 捕获  │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         │  HTTPS
                 ┌───────▼────────┐
                 │    服务端       │  一个普通 HTTP 服务
                 │  合并 / 搜索    │  跑在容器里
                 │  AI / 签发凭证  │
                 └───────┬────────┘
                         │
              ┌──────────┴──────────┐
              │                     │
      ┌───────▼───────┐     ┌───────▼───────┐
      │  PostgreSQL   │     │   对象存储     │
      └───────────────┘     └───────────────┘
```

**只有 Electron 是完整的本地优先端。** Web 纯在线。iOS 只有缓存和待传队列。

**合并只在服务端一份。** 客户端只做三件事：本地记变更、推、拉。

## 二、端的职责

| | Electron | Web | iOS |
|---|---|---|---|
| 本地库 | 完整 SQLite | 无 | 轻量缓存 + outbox |
| 全量对象 | ✅ | 按需 | 只缓存最近/常用 |
| 编辑附文 | ✅ | ❌ | ❌ |
| 捕获 | ✅ | ✅ | ✅ |
| 连接器 | ✅ | ❌ | ❌ |
| 大文件原件 | ✅ | ❌ | ❌ |
| 搜索 | 本地 FTS | 服务端 | 服务端 |
| AI | 走服务端 | 走服务端 | 走服务端 |
| 离线 | 满血 | 无 | 只读 + 捕获 |

**iOS 不实现合并、不实现段落编辑、不存版本。** 三个能力：拉取、显示、把捕获写进 outbox。

**冷启动 < 1 秒**，这是捕获能不能成立的硬指标。

## 三、数据模型

服务端为权威。所有表带 `user_id`，所有查询强制过滤。

```sql
users (id TEXT PRIMARY KEY, timezone TEXT, created_at BIGINT, settings JSONB);
```

**时区必须存。** 「今天 / 本周 / 本月」是本地时区的概念，服务端算不对就会把晚上 11 点记的东西算进第二天。

```sql
-- kind 的定义。第一版不给 UI 改，但存在库里，加一个不用发版
kinds (
  id TEXT PRIMARY KEY,       -- domain|project|canvas|group|
                             -- action|artifact|
                             -- distill|material|thought|
                             -- self|ai_output
  label TEXT, icon TEXT, color TEXT,
  properties JSONB,          -- 专属属性声明，见下
  parent_allowed TEXT[],     -- 能挂在哪些 kind 下面
  sort INTEGER
);
```

`properties` 的形态。**属性类型只有六种**，够用且不膨胀：

```json
{
  "status":   { "type": "label",    "options": ["todo","doing","blocked","done"] },
  "due_at":   { "type": "datetime" },
  "estimate": { "type": "number" },
  "done":     { "type": "checkbox" },
  "note":     { "type": "text" },
  "owner":    { "type": "object",   "kinds": ["self"] }
}
```

它决定三件事：**属性面板渲染什么控件、哪些字段可筛、默认视图用哪些列。**

**`label` 是类型内的固定选项集**，和 `object_tags` 的分工不能混：

| | `label`（在 properties 里声明） | `tags`（`object_tags` 表） |
|---|---|---|
| 范围 | 绑定一个 kind | 跨所有 kind |
| 值域 | 预设，校验 | 自由字符串 |
| 索引 | 可做列级索引 | 单独的表 |

**声明在 `properties` 里的字段，常见的做成 `objects` 上的独立列**（如 `status` / `due_at`，要索引要排序）；**罕见的走 `objects.extra` JSONB**，不建列。

**加一个 kind = 插一行 `kinds` + 写一份 `properties`。不改代码、不发版。** 三个端都从这张表读定义。

**十一个 kind，五类：**
- **容器** — `domain`（领域）/ `project`（项目）/ `canvas`（画布）/ `group`（分组）
- **执行** — `action`（行动，有流转）/ `artifact`（产物，不可变）
- **知识** — `distill`（沉淀，可升版）/ `material`（资料）/ `thought`（想法）
- **自我** — `self`（自我认知）
- **不是你写的** — `ai_output`（AI 生成的洞察、总结、扩写、批注）

**最后两类是同一类**：`material` 来自外部，`ai_output` 来自 AI，**都不是用户写的**。同一条规则适用：**都不能直接变成 `distill`，要升格必须用户用自己的话重写。**

**两组配对**：`thought → action`（澄清的两端，模糊的进想法，清楚了变行动）、`distill → artifact`（可复用的判断 vs 不可变的交付）。

**`action` 的硬约束**：它必须是一个无歧义的下一步。GTD 的原话是「模糊的条目会持续触发压力，清晰的下一步触发行动」。所以 `action` 需要一个 `status` 流转字段，而模糊的东西应该是 `thought`。

**`ai_output` 的硬约束**：它只能**新增**，不能修改任何已有对象的 `title` / `body`。AI 提议改属性走 `proposals`，产出内容走新对象 + 引用。

```sql
objects (
  id            TEXT PRIMARY KEY,   -- 客户端生成的 UUID
  user_id       TEXT NOT NULL,
  kind          TEXT,               -- NULL = 未提炼
  form          TEXT NOT NULL,      -- text|image|audio|video|link|canvas
  title         TEXT,               -- 主体
  body          TEXT,               -- 附文 Markdown 源文本
  body_blocks   JSONB,              -- 附文段落数组
  parent_id     TEXT,               -- 归属，唯一
  series        TEXT,
  tags_cached   TEXT[],             -- 冗余，加速筛选；权威在 object_tags
  status        TEXT,               -- 流转状态（行动等需要流转的 kind 用）
  due_at        BIGINT,
  sort_key      TEXT,               -- 分数索引
  supersedes_id TEXT,               -- 推翻：指向被取代的旧对象
  applies_to    TEXT[],             -- 适用范围（自我认知等必需）
  ephemeral     BOOLEAN DEFAULT false,
  asset_id      TEXT,               -- form != text 时的主体资产
  source_id     TEXT,               -- 来自哪个 source（连接器或 agent）
  source_ref    TEXT,               -- 外部稳定 id
  source_version TEXT,              -- 外部版本 / digest
  extra         JSONB,              -- 专属属性的值：kind 的 + source 的
  captured_at   BIGINT,             -- 客户端捕获时刻
  confirmed_at  BIGINT,             -- 最后一次「我还这么想」
  valid_until   BIGINT,
  rev           INTEGER NOT NULL,   -- 服务端分配的单调版本
  created_at    BIGINT,             -- 服务端接收时刻
  updated_at    BIGINT,
  deleted_at    BIGINT,             -- 软删（墓碑）
  search_vector tsvector
);
```

**两个时间必须分开。** 时间轴用 `captured_at`（否则离线捕获会全堆到上传那一刻），排序稳定性用 `created_at` 兜底。

**`assets` 的 `body_blocks`**

```json
{ "blocks": [
  { "id": "uuid", "key": "a0", "text": "第一段" },
  { "id": "uuid", "key": "a1", "text": "第二段" }
] }
```

`key` 是分数索引（可比较的字符串，插入时取两侧中间值）。**不要用数组下标**——两端在中间各插一段会错位。

```sql
object_tags    (object_id TEXT, tag TEXT, user_id TEXT, deleted_at BIGINT);
object_aliases (object_id TEXT, alias TEXT, user_id TEXT);
relations      (from_id TEXT, to_id TEXT, user_id TEXT, created_at BIGINT,
                source_field TEXT,      -- title | body
                source_block_id TEXT,   -- 哪个段落发出的
                deleted_at BIGINT);
```

### 关系与图

只有一种关系：**引用**。但两个方向要分开查，而且**索引是必须的**：

```sql
CREATE INDEX ON relations (from_id) WHERE deleted_at IS NULL;
CREATE INDEX ON relations (to_id)   WHERE deleted_at IS NULL;
```

**单对象图**（打开一个对象看它的关联）：

- 出边 `from_id = X` —— 它引用了谁
- 入边 `to_id = X` —— 谁引用了它
- **默认一跳，允许展开到两跳。** 两跳以上节点指数增长，看不出结构
- **两个方向要用颜色或左右分列区分**——「我引用了它」和「它引用了我」是不同信息

**不进图的东西**：分组和画布（它们在 `placements`，不在 `relations`）、来源（那是溯源，放详情页的「来自」一行）。

**不做全局图。** Capacities 明确不做——节点太多，看不出东西。全局结构交给**认知地图**（第十一节），它显示的是"内容算出的主题"，比"你连过什么"更接近真实。

**图会非常稀疏。** 对象数以万计，引用可能只有几千条——大部分对象打开时图是空的。**空状态要明确写「这条还没有关联」，不要画一个孤立的点。**

**`source_field` / `source_block_id` 的额外价值**：图里不只能显示「A 引用了 B」，还能显示「**A 的第三段**引用了 B」，点边能跳回原文那一句。这是 Capacities 的对象级引用没有的深度。

**`source_field` / `source_block_id`** 让引用能溯源，也让它随段落删除一起清理。

```sql
placements (
  canvas_id TEXT, object_id TEXT,
  x REAL, y REAL, w REAL, h REAL, z INTEGER,
  display TEXT,        -- NULL=跟随全局 | title_only | collapse_body | full
  user_id TEXT,
  PRIMARY KEY (canvas_id, object_id)
);
```

**没有 `group_id`。** 分组自带成员（见第四节）。

```sql
assets (id TEXT, user_id TEXT, hash TEXT, size BIGINT, mime TEXT,
        storage_key TEXT, thumb_key TEXT,
        width INTEGER, height INTEGER, duration INTEGER, created_at BIGINT);

object_assets (object_id TEXT, asset_id TEXT, role TEXT);  -- main | inline
```

`role = inline` 是附文里的 `![](asset://xxx)`。

```sql
versions (object_id TEXT, rev INTEGER, snapshot JSONB, created_at BIGINT, user_id TEXT);

conflicts (id BIGSERIAL, user_id TEXT, object_id TEXT, field TEXT,
           base_rev INTEGER, server_rev INTEGER,
           resolution TEXT,      -- lww | block_merge | lost
           device_id TEXT, created_at BIGINT);
```

**`resolution = 'lost'` 的必须能在界面上看到**，否则就是静默丢数据。

```sql
distill_sessions (id TEXT PRIMARY KEY, user_id TEXT, created_at BIGINT, scope JSONB);

proposals (id BIGSERIAL, session_id TEXT, object_id TEXT, field TEXT,
           ai_value TEXT, final_value TEXT,
           status TEXT,        -- accepted | edited | rejected | pending
           decided_at BIGINT, user_id TEXT);
```

**`ai_value` 和 `final_value` 的差异就是你的判断模式记录。**

```sql
-- 同步
changes (seq BIGSERIAL, user_id TEXT, device_id TEXT, object_id TEXT,
         field TEXT, value TEXT, base_rev INTEGER, client_ts BIGINT, created_at BIGINT);
devices (id TEXT PRIMARY KEY, user_id TEXT, name TEXT, last_seq BIGINT, last_seen BIGINT);

-- 连接器与 AI agent 共用一张表
sources (id TEXT PRIMARY KEY, user_id TEXT,
         type TEXT,        -- connector | agent
         connector TEXT,   -- codex | obsidian | chrome | xiaohongshu | twitter | ...
         name TEXT,
         properties JSONB, -- 这个来源产出的对象有哪些专属字段（见下）
         config JSONB, anchor JSONB, state JSONB,

-- 检索
embeddings (object_id TEXT, chunk_id TEXT, model TEXT, vec vector(1024), user_id TEXT);
```

## 四、分组与画布布局

**分组是「区域」，不是「集合」。** 已确定。

```sql
ALTER TABLE placements ADD COLUMN group_id TEXT;  -- 指向同画布上的分组对象
```

- **成员是每张画布各自的**——在 A 画布上往框里加东西，不影响 B 画布
- **复用的是容器本身**（名字、颜色），不是成员
- **成员无序**——顺序由摆放决定。加第二套排序会和画布打架
- 渲染时对画布上每个对象反查一次「它被哪个分组引用」，批量查一次

**如果你需要跨画布的「一组东西」，不该用分组**——用一个对象引用那一组即可（`relations` 本来就能做）。

**用数据表达集合，用分组表达布局。**

### 嵌套与防环

写入 placement 前，从目标画布向上遍历「我在哪张画布上」，遇到要放入的对象就拒绝。写时检查，深度很浅。

**面包屑不进数据库。** 一个对象能在多张画布上，路径不唯一，只显示**当前这条**——用客户端的导航栈。

**删除画布不删内容。** placement 消失，对象还在。

## 五、连接器

```ts
interface Connector {
  connector: string                   // codex | obsidian | chrome | ...
  config: JSONB                       // 路径、profile、账号
  state: JSONB                        // 上次错误、连续失败次数

  fetch(anchor: unknown | null): Promise<{
    items: RawItem[]
    nextAnchor: unknown
  }>
}

interface RawItem {
  ref: string        // 外部稳定 id
  version: string    // 外部版本 / digest
  form: 'text' | 'link' | 'image' | 'audio' | 'video' | 'file'
  title?: string
  body?: string      // 已经转成 Markdown
  capturedAt: number // 外部时间，不是拉取时间
  asset?: { localPath?: string; url?: string; mime?: string }
  extra?: JSONB      // 连接器特有，只读展示
}
```

**六条规则**

1. **`anchor` 是不透明数据。** 服务端只存不解释。Codex 用最后会话 id，Obsidian 用「文件 → mtime」的 map，Chrome 用最后访问时间。**加一种连接器不用改服务端。**
2. **归一化在连接器内部完成。** `[[ ]]`、会话 JSON、SQLite 行，都在这里变成 Markdown。翻译完系统只认 `RawItem`。
3. **聚合粒度是连接器的责任。** Obsidian：一个文件；Codex：一次会话；**Chrome：一次浏览会话**（同域名、间隔 < 30 分钟）。Chrome 不聚合会淹掉系统。
4. **`extra` 是逃生舱。** 连接器特有的字段不进 `objects` 表。
5. **连接器跑在 Electron。** 数据源都在本机。拉完归一化，走正常 push。
6. **资产由连接器下载**，算 hash，走上传链路。

**锚点语义：展开即视为看过**——锚点前移，UI 不再高亮。**不代表任何操作。**

**`state` 不能省。** 外部源会变（路径改了、profile 换了）。没有它，失败会静默——你会以为连接器在工作，其实三周没拉到东西。**连接器没产出本身应该是可见的。**

### 来源的专属字段

连接器产出的对象带专属字段（小红书有点赞数、Twitter 有转发数）。**值存 `objects.extra`，schema 声明在 `sources.properties`**：

```json
{
  "likes":     { "type": "number" },
  "author":    { "type": "text" },
  "posted_at": { "type": "datetime" }
}
```

**和 `kinds.properties` 是同一套机制、同一份属性类型清单**（第六节）。没有它，`extra` 就是一堆 UI 猜不出怎么渲染的数据。

**渲染按 `connector` 选组件：**

```
xiaohongshu   → 图文卡片
twitter       → 短文本 + 作者
自己的对象     → 默认组件
```

这是 UI 层的约定，但数据层要能查到：`objects.source_id → sources.connector`。

**来源是唯一的**（一个对象只有一个 `source_id`），所以渲染没有歧义。**加一个新平台 = 插一行 `sources` + 写一份 `properties`，不改代码、不加 kind。**

## 六、同步协议

```
POST /sync/push
{ device_id, changes: [{ object_id, field, value, base_rev, client_ts }] }
```

服务端逐条：

```
对象不存在             → 创建，rev = 1
base_rev == 当前 rev   → 直接应用，rev + 1
否则                   → 冲突，走第七节合并，rev + 1
```

写入前把当前状态存一份进 `versions`。

```
POST /sync/pull  { device_id, since_seq }
→ { changes, latest_seq, objects, assets }
```

`since_seq` 是每个设备记的 `last_seq`。增量，不拉全量。

**`changes.seq` 由服务端分配，全局单调。客户端的时钟只用于合并平局，不用于排序。**

## 七、合并规则

| 字段 | 策略 |
|---|---|
| `title` / `body` | LWW，比 `client_ts`，平局比 `device_id` |
| `body_blocks` | **按 block id 合并**：并集；同 id 冲突用 LWW |
| `kind` / `parent_id` / `series` / `status` / `due_at` | LWW |
| `tags` | 并集；删除用墓碑 |
| `relations` | 并集；删除用墓碑 |
| 删除对象 | 墓碑 wins |

段落级合并能处理：两端各加段、各删段、一端加一端删另一段。**唯一处理不了的：两端改同一段**——LWW，丢一边。单用户下概率接近零。

**冲突记录进 `conflicts`。`lost` 的必须可见。**

## 八、资产

**上传必须客户端直传，不经过服务端容器**（云托管包体上限 20M）。

```
1. 客户端 → POST /assets/sign { size, mime, hash }
2. 服务端返回 { asset_id, storage_key, upload_token }
     storage_key = {user_id}/{asset_id}
3. 客户端直传对象存储
4. 客户端 → POST /assets/commit { asset_id, hash, size, thumb }
```

**存储路径由服务端下发，客户端不能自己拼**——否则可以伪造路径写到别人的目录。

读用临时签名 URL，有时效。

`hash` 是明文内容哈希，由客户端算，**只用于用户内部去重**。

## 九、认证与隔离

每个请求带 token，服务端解析出 `user_id`。

**所有查询强制带 `user_id`，在数据访问层做一次，不靠每个查询记得写。**

存储路径含 `user_id`。`user_id` 从第一天就进 schema 和路径。

**同一时间只能连一个后端。** 桌面连自托管、手机连 CloudBase 等于两个真相源。

## 十一、搜索

**两个通路，共用一张表，不是两条技术路线。**

| 通路 | 解决 | 技术 |
|---|---|---|
| 字面 | 精确找 | `pg_trgm` GIN（P0）→ BM25（P3） |
| 语义 | 「这条和三个月前那条很像」 | `pgvector` + `bge-m3`（P1） |

**为什么不能只用一个**：embedding 会漏精确匹配（Anthropic 官方结论）；而跨时间找相似**没有可 grep 的共享词串**，且是穷举发现不是「找到即止」——**这正是 Claude Code 选 grep 的两个前提在你这里失效的地方**。

**分阶段**

- **P0（一个下午）** —— `pg_trgm` GIN 索引。中文下 trigram = 3 字滑窗，对自造词友好、天然支持子串。
- **P1（唯一必须跨的坎）** —— 加 `pgvector` + `bge-m3`（1024 维，8192 token 上限）离线批量嵌入一次。**先不开 ANN 索引**：5 万条 ≈ 200MB，精确搜索几十到几百毫秒，recall 100%。
- **P2** —— HNSW（如果按时间/标签过滤后再搜，要配 `hnsw.iterative_scan=relaxed_order`）；长文档切块。
- **P3** —— 词法升 BM25。**中文首选 ParadeDB `pg_search`**（原生 `pdb.jieba`，不用编译 SCWS）。**不要用 `pg_jieba`（停更三年）。** 保留 `pg_trgm` 兜底——分词器切错时字面通路还能命中。
- **P4** —— 检索 tool 化给 agent。**必须设预算上限**（Anthropic 自己踩过「为简单查询生成 50 个子 agent」的坑）。**精确查找不要走 agent。**

**rerank 比调阈值有效得多**（+5–10 点 nDCG）。阈值 0.8 是先拍的，见遗留。

**语料规模的硬事实**：PG 自带的全文检索**对中文不可用**（无 CJK 切分，整句一个 token）。

## 十二、AI 洞察

**纯 pull。没有定时，没有推送，没有红点。**

```
POST /insight { scope: {...} }
→ { text, citations: [object_id...], silent: boolean }
```

- **允许沉默**：证据不足或没有明显张力时返回 `silent: true`，界面什么都不显示
- **输出不落库。** 它是临时的、可看不可存。要留下，用户自己重写
- **必须带引用**，能点回原对象
- **只基于已有内容，不引用外部信息**

**这和 `proposals` 是两回事**：Proposal 是对某个对象的字段建议，要存（它是判断记录）；洞察报告是对一组对象的分析，不存（它会污染语料）。

**标签只归一，不凭空创建。**

## 十三、双后端

同一份服务代码，两个独立契约，各自选择实现：

```ts
interface Auth   { verify(token): Promise<userId> }
interface Assets { sign(key, ttl), commit(id, hash), url(id, ttl) }
// Store 两边都是 Postgres，直接用 pg.Pool，不需要抽象
```

| | CloudBase | 自托管 |
|---|---|---|
| 计算 | 云托管（Docker 容器） | Docker |
| 数据库 | 云开发 PostgreSQL | 同版本 Postgres |
| 存储 | 云存储 HTTP API | S3 / MinIO |
| 认证 | 云开发身份认证 | 自建 JWT |

**只有认证和存储凭证要写两套。** 连库是同一行代码。

表中是常见组合，不是绑定关系。`AUTH_MODE=password|cloudbase` 独立选择认证，`STORAGE_DRIVER=s3|cloudbase` 独立选择附件存储，数据库由 `DATABASE_URL` 决定。MinIO、COS、S3、R2 使用同一个 S3 适配器，通过端点/桶/区域/寻址方式配置；供应商兼容性需实际验收。计算可运行在任意支持该容器的平台。

旧 `BACKEND` 只为未设置的独立选项提供默认值。认证切换须维持用户 ID 映射；存储切换须迁移原文件、保留 `storage_key`，不能将修改环境变量等同于完成数据迁移。部署入口及操作见 `DEPLOYMENT.md`。

### CloudBase 的实际约束（已核实）

- 请求超时 **60s**、包体 **20M**
- 一个环境最多 **15 个服务**、**28 个实例**；QPS 受环境总量限制
- 最小副本可设为 **0**（30 分钟无流量后缩容）
- **必须开启环境的「超限按量」，否则服务会被停**
- ⚠️ **长期不活跃的资源会被冻结，解冻后必须重新部署版本**
- 地域上海；备案需要个人版及以上、剩余有效期 ≥ 6 个月、开启云托管固定 IP
- 支持的扩展：`pgvector` + `vectorscale`、`zhparser` / `pg_jieba`、`pg_trgm`

## 十四、Schema 演进

- 新增字段一律可选，**永不删字段**
- 服务端必须能读**任意客户端版本**提交的数据
- 每次结构变更配一个迁移函数
- 服务端版本号控制最低客户端要求

**预留**：客户端和服务端之间的「值」是一个独立载荷，现在是明文 JSON，以后可以是密文。加端到端加密时只改载荷的编解码，不动结构。

## 十五、迁移契约

**适配器可以通过环境变量独立切换；已有数据库、文件和用户归属仍需迁移与校验。** 下面是不变量——破坏任何一条都会让迁移变贵。

### 接缝只有一个

```
业务数据 ←→ user_id 字符串 ←→ 认证源
              ↑ 唯一接缝
```

- `user_id` 统一 **`varchar(64)`**，与 CloudBase `auth.users.id` 同型
- **`objects.user_id` 不建指向 `users` 的外键**。租户边界由 RLS 保证；没有外键，换认证源时业务表一行都不用动
- `users` 是**档案表**（时区、偏好），不是身份表

### 登录态用 CloudBase 的变量名

```sql
auth.uid()  →  current_setting('request.jwt.claims')::jsonb ->> 'sub'
```

自托管由服务端 `set_config` 写入，CloudBase 由网关注入。**同一份函数定义、同一份 RLS 策略，两边通用。**

claims 未注入时 `auth.uid()` 返回 NULL，`user_id = NULL` 求值为 NULL——**失败方向是「看不见」而不是「看得见」。**

### 五个替换点，其中两个是代码

| 层 | 自托管 | CloudBase | 改动 |
|---|---|---|---|
| **认证** | `AUTH_MODE=password` | `AUTH_MODE=cloudbase` | 环境变量 |
| **存储** | `STORAGE_DRIVER=s3` | `STORAGE_DRIVER=cloudbase` | 环境变量，与认证独立 |
| 数据库 | 自建 Postgres | 云开发 PostgreSQL | `pg_dump` + `pg_restore` |
| 文件 | MinIO | 云存储 | `rclone`——**`storage_key` 是 `{user_id}/{asset_id}`，两边通用，DB 不用改** |
| embedding | 外部 API | 同左，或 `tencentdb_ai` Auto Embedding | 环境变量 |

### SQL 文件的排列方式就是迁移顺序

```
000_extensions.sql    两套后端都支持；CloudBase 可能需在控制台先启用
001_schema.sql        表与索引
002_kinds.sql         种子数据
003_auth_compat.sql   auth schema + auth.uid()，与 CloudBase 对齐
004_migrate.sql       已有安装的幂等升级（先删策略 → 改类型 → 去外键）
005_rls.sql           建租户策略
```

**`004` 必须在 `005` 之前**——PostgreSQL 不允许修改被 RLS 策略引用的列的类型。这个顺序已经在真实数据库上验证过。

`004_migrate.sql` 里去掉外键时只能按 `confrelid = 'users'` 精确匹配：`objects` 上还有两个自引用外键（`user_id,parent_id` 和 `user_id,supersedes_id`），**它们的键里也含 `user_id`，按列名匹配会把它们一起误删。**

### 迁移清单

```bash
pg_dump --no-owner --no-privileges drill > drill.sql
psql "$CLOUDBASE_DATABASE_URL" -f infra/sql/001_schema.sql
psql "$CLOUDBASE_DATABASE_URL" -f drill.sql
# 文件通过源/目标对象存储 API 复制并校验，不复制 MinIO 底层数据目录。
# 保持 storage_key 和元数据，先复制验证，再切换，不删除旧桶。
AUTH_MODE=cloudbase
STORAGE_DRIVER=cloudbase
```

**`000_extensions.sql`、`003_auth_compat.sql`、`004_migrate.sql`、`005_rls.sql` 在 CloudBase 上可能没有权限执行**——托管实例的扩展、角色和 `auth` schema 由平台管理。以控制台的实际能力为准。

### 两处**还没**对齐

1. **`CloudBaseAssets` 的返回契约没验证过**——它猜了三种字段形状（`signedURL ?? signedUrl ?? url`），这是迁移时第一个会撞的
2. **CloudBase 的 `auth.users` 密码哈希算法未知**——所以现在**不自建密码认证**。密码是唯一「导出后可能没用」的数据，其余都能搬
